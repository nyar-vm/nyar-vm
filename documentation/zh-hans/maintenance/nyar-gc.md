# nyar-gc

`nyar-gc` 提供了一个专为 Nyar VM 优化的垃圾回收器。其设计深受 **Alloy GC** 的启发，将 Rust 的所有权模型与高效的垃圾回收机制深度整合。

## 托管语言的内存模型

`nyar-gc` 的核心设计哲学是 **"RAII + GC"**。这一理念主要应用于托管在 NyarVM 上的高级语言（如 [rusty-c](file:///e:/普遍优化/nyar-vm/examples/rusty-c), [rusty-java](file:///e:/普遍优化/nyar-vm/examples/rusty-java) 等），使其能够享受到与 Rust 同等级别的资源管理能力。

> **注意**: 根据 Alloy GC 的原始论文，要让 Rust 语言本身实现这一特性需要修改 `rustc` 编译器。但在 NyarVM 生态中，由于我们完全掌控了托管语言从源代码到字节码的**编译全流程**，我们可以在不修改 Rust 编译器的情况下，为托管语言实现这些先进的内存管理特性。

### 1. 资源获取即初始化 (Resource Acquisition Is Initialization)

在传统的 GC 托管语言（如 Java, Python）中，RAII 往往难以实现，因为对象的生命周期由 GC 异步管理，导致非内存资源（如文件句柄、数据库连接）的释放时机不可控。

在 NyarVM 托管语言中，RAII 得到了原生支持：
- **生命周期绑定**: 托管语言的编译器在生成 UIR 时，会自动注入资源的初始化与绑定逻辑。
- **确定性范围**: 即使对象分配在托管堆上，其引用的生命周期依然可以受到托管语言编译器生成的静态分析约束。
- **资源安全**: 开发者可以像使用 Rust 一样，通过获取即初始化的模式来管理所有系统资源，而不必担心泄露。

### 2. 析构函数即终结器 (Destructor as the Finalizer)

- **核心机制**: 托管语言中的对象在被 GC 回收时，会触发其对应的析构逻辑。在底层，这通过 Rust 的 `Drop` trait 实现：每个托管在堆上的 `GcBox` 都关联了其原始类型的析构函数。
- **即时性与确定性**: 当 GC 判定一个对象不再可达时，会**立即且仅一次**地调用其析构函数（`drop_in_place`）。
- **Alloy 方案的优势**: 这种析构即终结的模式彻底解决了传统 GC 语言中 `finalize` 机制执行时机不确定、对象复活 (Resurrection) 等顽疾。
- **FFI 友好**: 这使得托管语言可以安全地持有通过 FFI 获取的非托管资源。当托管对象死亡时，GC 会确保调用相应的释放函数（如 `free` 或 `close`），实现了跨语言边界的确定性资源管理。

## 现代并发模型下的 GC 挑战

随着协程 (Coroutines)、异步 (Async/Await)、代数效应 (Algebraic Effects) 以及 JIT 技术的普及，GC 策略正在经历深刻的变革。`nyar-gc` 在设计时也充分考虑了这些前沿趋势：

### 1. 堆分配栈与微根管理
-   **趋势**: 传统 GC 假设根集合（Roots）主要是少量的线程栈。但在现代并发模型（如 Go 的 Goroutines 或 Java Loom）中，可能存在数百万个协程。
-   **挑战**: 传统的 Stop-the-world 扫描数百万个协程栈会造成巨大的停顿。
-   **演进**: 现代 GC 将协程栈视为堆上的普通对象（Activation Records）。`nyar-gc` 采用**并发根扫描 (Concurrent Root Scanning)** 技术，允许在 VM 运行的同时逐步扫描这些微根，极大地降低了初始停顿。

### 2. 代数效应与延续 (Continuations) 的追踪
-   **趋势**: 代数效应允许捕获并重新执行执行上下文（延续）。
-   **影响**: 延续在堆中形成了复杂的、可能被多次引用的对象子图。
-   **演进**: 为了支持多跳延续 (Multi-shot Continuations)，`nyar-gc` 的追踪算法支持对延续路径的持久化引用管理，确保被捕获的上下文在逻辑结束前不会被错误回收。

### 3. JIT 与 GC 的深度协同
-   **安全点 (Safepoints)**: JIT 编译器在生成的机器码中精确插入安全点。对于异步代码，每一个 `yield` 点本质上都是一个隐含的安全点。
-   **逃逸分析 (Escape Analysis)**: 通过 JIT 的逃逸分析，我们可以判定某些协程帧是否会逃逸出其作用域。未逃逸的帧可以直接分配在物理栈上而非托管堆，从而减轻 GC 压力。
-   **代码缓存 GC (Code Cache GC)**: 随着 JIT 生成的代码量增加，`nyar-gc` 也会对不再使用的机器码片段进行回收。

### 4. 屏障技术的极致优化
-   **趋势**: 零停顿 GC（如 ZGC, Shenandoah）依赖于复杂的读/写屏障。
-   **演进**: 在异步频繁切换的环境下，屏障的开销会被放大。`nyar-gc` 借鉴了 **染色指针 (Colored Pointers)** 和 **自愈屏障 (Self-healing Barriers)** 技术，通过在指针中编码元数据，将屏障的判断逻辑降至最低，甚至在某些情况下实现“零开销屏障”。

## 核心设计：三色标记法 (Tri-color Marking) [已实现]

为了实现无暂停 (Zero-pause) 或低延迟回收，`nyar-gc` 采用了标准的三色标记算法：

-   **白色 (White)**: 候选回收集合。初始时所有对象为白色。若标记结束仍为白色，则视为垃圾。
-   **灰色 (Gray)**: 波面 (Wavefront) 对象。已标记为活跃，但其子节点尚未扫描。
-   **黑色 (Black)**: 已扫描集合。对象活跃且其子节点已全部扫描，不会再被扫描。

**写屏障 (Write Barrier)**: 为了维持强三色不变性（黑色对象不能直接指向白色对象），我们在修改对象引用时插入屏障。如果发生此种赋值，屏障会将目标白色对象着色为灰色，确保扫描的一致性。

## 全方位的 GC 优化技术

除了基础的标记-清除，现代 GC 还有以下成熟的优化手段，`nyar-gc` 正在逐步引入：

### 1. 吞吐量优化
-   **分代假设 (Generational Hypothesis) [已实现]**: 基于“大部分对象朝生夕死”的观察。将堆分为 Young 和 Old 区，频繁回收 Young 区，显著减少每次回收需要扫描的对象数量。
-   **碰撞指针分配 (Bump Pointer Allocation) [已实现]**: 在连续内存空间中分配，仅需移动指针。配合**压缩式 GC (Compacting GC)** 解决内存碎片问题。
-   **线程本地分配缓冲区 (TLAB)**: 每个线程预留一块私有内存，分配时无需加锁，极大地提升多线程下的分配性能。

### 2. 延迟与响应优化
-   **并发清除 (Concurrent Sweeping)**: 标记阶段完成后，清除工作可以与用户程序并行，因为不可达对象不会再变为可达。
-   **增量标记 (Incremental Marking) [已实现]**: 将巨大的标记任务分解为多个小步，交替运行 GC 和用户程序，避免长时间的 STW (Stop-the-world)。

### 3. 内存效率优化
-   **指针压缩 (Pointer Compression)**: 在 64 位系统上使用 32 位相对偏移量存储指针，减少 GC 根集合扫描的开销并降低缓存未命中率。
-   **卡表 (Card Table) [已实现]**: 使用位图（1 个 bit 代表 512 字节内存）来标记“脏”内存区域。相比 `Remembered Set`（存储对象列表），卡表在老生代引用新生代对象时，扫描效率更高，写屏障开销更小。

### 4. 精确性优化
-   **栈图 (Stack Maps)**: 由编译器生成，告知 GC 栈帧中哪些位置是真正的指针。这避免了保守式 GC (Conservative GC) 将普通整数误判为指针，从而允许进行对象移动（压缩）。

## 回收机制

### 1. 标记阶段 (Marking Phase)
- **三色标记状态机**: 维持强三色不变性，确保并发安全。
- **根集合追踪**: 从解释器栈、局部变量表、全局变量等根节点出发。
- **写屏障 (Write Barrier)**: 拦截黑色对象对白色对象的引用。

### 2. 清除阶段 (Sweeping Phase)
- **自动析构**: 对于未标记的对象，GC 会自动调用其绑定的 Rust 析构函数。
- **内存回收**: 释放 `GcBox` 占用的堆内存。
- **对象晋升**: 经历过多次回收仍存活的新生代对象会被晋升到老生代。
