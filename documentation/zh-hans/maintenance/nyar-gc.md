# Nyar Garbage Collector (nyar-gc)

`nyar-gc` 是一个专为 Nyar VM 优化的、高性能、低延迟的垃圾回收器。其设计深受 **Alloy GC** 的启发，旨在将 Rust 的所有权模型与高效的托管内存管理机制深度整合。

## 核心架构与设计哲学

### 1. 托管语言的内存模型：RAII + GC

`nyar-gc` 的核心设计哲学是 **"RAII + GC"**。这一理念主要应用于托管在 NyarVM 上的高级语言（如 [rusty-c](file:///e:/普遍优化/nyar-vm/examples/rusty-c), [rusty-java](file:///e:/普遍优化/nyar-vm/examples/rusty-java) 等），使其能够享受到与 Rust 同等级别的资源管理能力。

- **生命周期绑定**: 托管语言的编译器在生成 UIR 时，会自动注入资源的初始化与绑定逻辑。
- **确定性析构 (Destructor as Finalizer)**: 托管对象在被回收时，会立即触发其对应的 Rust `Drop` 逻辑。这种机制解决了传统 GC 语言中 `finalize` 执行时机不确定、对象复活 (Resurrection) 等问题，且对 FFI 极其友好。

### 2. 非移动式设计 (Non-moving Design)

与 Java (G1/ZGC) 等移动式 GC 不同，`nyar-gc` 选择了 **非移动式** 架构。对象在分配后，其内存地址在整个生命周期内保持固定。

#### 为什么不移动对象？
- **NaN-Boxing 极致性能**: NyarVM 使用 NaN-Boxing 存储 [Value](file:///e:/普遍优化/nyar-vm/projects/nyar-vm/src/vm/value.rs)。非移动式设计允许直接在 `Value` 中存储原始指针。如果移动对象，更新所有嵌入在浮点数位模式中的指针将带来巨大的解包/重定位开销。
- **Rust FFI 友好**: 大量 Nyar 托管对象直接与 Rust 原生代码交互。非移动式设计避免了复杂的“固定 (Pinning)”机制，原生代码持有的指针始终有效。
- **RAII 确定性**: 对象的物理位置固定，使得 `Drop` 逻辑的执行更加安全，不会因为 GC 整理内存而导致 `self` 指针失效。

### 3. 与 VM 的深度协同：NaN-Boxing

NyarVM 使用 **NaN-Boxing** 技术来表示通用 [Value](file:///e:/普遍优化/nyar-vm/projects/nyar-vm/src/vm/value.rs)。
- **指针嵌入**: 所有的托管对象指针都嵌入在 64 位浮点数的非有效位（Payload）中。
- **快速追踪**: GC 在扫描栈时，可以通过位运算快速识别并提取出 `GcHeader` 指针，从而进行标记。

## 垃圾回收算法：基于块的增量三色标记 [已实现]

为了平衡吞吐量与停顿时间，`nyar-gc` 实现了基于块管理（Block-based）的增量三色标记算法，废弃了复杂的分代逻辑以换取更高的分配性能和更简洁的代码实现。

### 1. 三色标记状态机
- **白色 (White)**: 初始状态，潜在的回收对象。
- **灰色 (Gray)**: 已标记但其引用对象尚未扫描，处于“波面”。
- **黑色 (Black)**: 已扫描且其引用对象也已处理，存活对象。

### 2. 写屏障 (Write Barriers)
为了在增量标记期间维持三色不变性，`nyar-gc` 使用了增量写屏障策略：
- **增量屏障 (Incremental Barrier)**: 
    - **Dijkstra 风格**: 在 `write_barrier` 和 `write` 操作中，当 GC 处于标记阶段（Marking）时，将新写入或被引用的子对象立即涂灰并加入标记栈。这确保了在增量扫描过程中，新产生的引用关系不会被遗漏。

### 3. 扫描策略：块线性扫描 (Block Linear Scanning)
- **非分代设计**: 移除了原有的新生代/老生代概念及对象晋升逻辑。所有对象在所属的 `GcBlock` 内按地址顺序线性存放。
- **增量清理**: 清理阶段（Sweeping）被分散到多次步进执行中。GC 追踪当前的块指针（`block_curr`）和块内游标（`block_cursor`），每次 `step()` 只扫描固定数量的对象。
- **存活统计**: 标记阶段结束后，存活对象的字节数会被汇总到所属块的 `live_bytes` 中，作为回收块的依据。

## 如何在非移动架构下实现高性能？

虽然不移动对象，但 `nyar-gc` 通过以下技术确保了接近甚至超过移动式 GC 的性能：

### 1. 块式管理与分配优化
- **碰撞指针 (Bump Pointer)**: 在所有 [GcBlock](file:///e:/普遍优化/nyar-gc/src/lib.rs#L30) 内分配仅需简单的指针加法，性能等同于栈分配。
- **线性扫描规避碎片**: 虽然不移动对象，但通过按块线性扫描和 TLAB 结合，在高频分配场景下能有效维持内存紧凑性。未来将引入按对象大小分类的分配池（Size-segregated Storage），进一步消除长期运行后的内存碎片。

### 2. TLAB 实现细节
- **本地缓冲区**: 每个线程分配一个 64KB 的本地缓冲区（TLAB）。
- **碰撞指针分配**: TLAB 内部使用碰撞指针进行分配，无需任何同步开销。
- **慢速路径**: 当 TLAB 耗尽时，线程会向全局 GC 申请一个新的 TLAB，此操作通过对 `GcBlock` 的 `cursor` 进行原子 `fetch_add` 实现，仅在跨块分配时需要短暂竞争。

### 3. 增量清理加速
- **无链表维护**: 扫描不再依赖复杂的双向链表或分代集合，直接在内存块上进行地址增加式的线性扫描。
- **Padding 快速跳过**: 通过对象头部的类型信息快速识别并跳过空隙（Padding），提升了大内存块的扫描效率。
- **存活字节追踪**: 每个块实时维护 `live_bytes` 原子变量，允许在清理阶段直接定位并释放完全空闲的块。

### 2. 零成本指针访问
- **无间接跳转**: 由于对象不移动，VM 访问对象属性时无需通过“句柄表 (Handle Table)”或“转发指针 (Forwarding Pointer)”。这减少了每次内存访问的延迟。

### 3. 增量与并发支持
- **低延迟 STW**: 通过增量标记，将 GC 停顿分散到多次微小的 `step()` 中，避免了移动式 GC 在压缩阶段动辄数十毫秒的全局停顿。
- **并行卡表扫描**: 卡表技术允许 Minor GC 极快地过滤掉老生代中不含跨代引用的区域。

## 内存布局与分配性能

### 1. 块式管理 (Block-based Memory)
- **1MB 对齐块**: 内存按 1MB (`BLOCK_SIZE`) 的粒度进行申请，并严格按照 1MB 边界对齐。
- **元数据嵌入**: 块的头部嵌入了 `GcBlockHeader`，包含原子游标、存活字节计数和卡表。
- **O(1) 元数据寻址**: 任意托管对象的指针 `p`，其所属块的头部地址即为 `p & !(1MB - 1)`。这消除了全局块查找的开销，使得写屏障几乎是零成本的。
- **动态回收**: 引入 `live_bytes` 原子追踪。当一个块内的所有对象都被回收时，GC 会在清理阶段结束时自动释放该内存块，动态归还给操作系统。

### 2. 分配优化
- **TLAB (Thread Local Allocation Buffer)**: 每个执行线程拥有独立的 64KB 本地缓冲区。
- **无锁分配**: 在 TLAB 内的分配仅需简单的指针加法。当 TLAB 耗尽时，才通过原子操作（Compare-and-Swap）从全局块中申请新空间，极大降低了多线程并发分配的锁竞争。
- **黑色分配 (Black Allocation)**: 在 GC 处于标记阶段时，新分配的对象会自动标记为黑色，避免其在当前周期被错误回收。

## 线程安全与并发

`nyar-gc` 从底层设计上支持多线程并发访问：

- **原子化状态机**: `GcHeader` 的颜色、代际以及 GC 本身的运行状态均采用原子类型管理，使用 `Acquire/Release` 内存序确保跨线程的同步。
- **Sync/Send 支持**: `Gc<T>` 实现了 `Send` 和 `Sync`，允许在线程间安全地传递托管引用。
- **并发链表维护**: 对象的链表插入使用无锁的 `compare_exchange` 逻辑，支持多个线程同时进行对象晋升或新对象录入。
- **细粒度锁**: 仅在必要的地方（如全局块列表、灰色栈、增量清理状态）使用细粒度锁，最大化并发吞吐量。

## 现代并发模型支持

`nyar-gc` 针对协程、异步及代数效应进行了特殊优化：

- **微根管理**: 将数百万个协程栈视为堆上的普通对象，支持并发根扫描，避免 STW。
- **延续追踪**: 支持对多跳延续 (Multi-shot Continuations) 的持久化引用管理，确保上下文安全。
- **JIT 协同**: JIT 编译器在生成的机器码中精确插入安全点 (Safepoints)，并在 `yield` 点进行隐式 GC 检查。

## 开发者指南

### 如何使类型可被回收？
所有需要在托管堆上分配的类型必须实现 `Trace` trait：

```rust
impl Trace for MyObject {
    fn trace(&self, ctx: &mut MarkContext) {
        self.some_field.trace(ctx);
        // 调用 ctx.mark() 标记内部的 Gc 指针
    }
}
```

### 使用建议
- **避免深层嵌套**: 过深的引用链会增加标记阶段的栈深度。
- **及时解除引用**: 尽量缩小 GC 对象的生命周期，有助于新生代回收。
- **配合 RAII**: 善用 `Drop` 处理非内存资源。
