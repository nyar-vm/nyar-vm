# Valkyrie VM Maintenance Guide

This guide is intended for **internal maintainers and the core development team** of the Valkyrie VM project. It introduces the project architecture, module responsibilities, internal maintenance processes, and system-level design decisions.

> **Target Audience**: Project maintainers, core development team members, system architects
> **Content Focus**: Internal architecture, maintenance processes, system design, code organization

## Project Architecture Overview

Valkyrie uses a Rust Monorepo (Workspace) architecture, where each component is encapsulated in an independent crate, providing clear dependency relationships, independent testing environments, and efficient parallel compilation.

```
valkyrie/
├── Cargo.toml         # Workspace root configuration
└── projects/
    ├── valkyrie-types/    # Unified intermediate representation type definitions (HIR, CFG, SSA, LIR)
    ├── valkyrie-compiler/ # Modern compiler framework based on Chomsky
    ├── valkyrie-runtime/  # Compiler passes and VM execution core
    ├── valkyrie-error/    # Diagnostic system based on miette
    └── legion/            # Command-line tool (Valkyrie toolchain entry point)
```

External Dependencies:
- `oak-valkyrie`: New frontend implementation (Lexer, Parser, AST), located in `../oaks`
- `ProjectChomsky`: Compiler backend optimization framework, located in `../ProjectChomsky`

## Core Design Philosophy

The architecture of Valkyrie is based on five design pillars:

### 1. 5-Stage Pipeline

A compiler is a process of performing a series of meaning-preserving transformations on program information, modeled as a pipeline of several carefully designed intermediate representations:

#### Stage 1: AST (Abstract Syntax Tree)
- **Responsibility**: Faithfully represent the syntax structure of the source code, preserving complete original information (such as SourceSpan) for diagnostics.
- **Current Implementation**: Uses `oak-valkyrie` as the unified frontend implementation.
- **Key Processing**:
  - **Macro Expansion**: Executes `@macro` and annotations `@.annotation`, generating new AST nodes.
  - **Template String Parsing**: Parses syntax structures like `f"hello {name}"` into AST expressions.
- **Optimization**: 
  - Very early constant folding (e.g., literal concatenation).
  - Syntax desugaring (e.g., `a += b` -> `a = a + b`).

#### Stage 2: HIR (High-level IR)
- **Responsibility**: Global semantic graph, containing complete type information, scopes, and name resolution results.
- **Key Processing**:
  - **Symbol Resolution**: 
    - Handles `using` imports, building cross-module symbol references.
    - Establishes namespace hierarchy, managing variable scopes and shadowing.
    - Binds function calls to specific function definitions, handling overload resolution.
  - **Macro Expansion and Attribute Processing**:
    - Executes `@macro` and annotations `@.annotation`, structurally reorganizing the AST at the semantic level.
    - Handles built-in attributes (e.g., `@inline`, `@tail_rec`).
  - **Type Checking & Inference**: Trait resolution and type inference based on the C3 linearization algorithm, ensuring type safety.
  - **Pattern Matching Desugaring**: 
    - Converts complex `match` structures into decision trees.
    - Generates exhaustiveness checks to ensure pattern matching completeness.
  - **Algebraic Effect Desugaring**: Maps `try/handle` structures to underlying control flow primitives.
- **Optimization**:
  - **High-level Inlining**: Reduces call overhead for small functions based on heuristic algorithms.
  - **Monomorphization**: Generates specialized code paths for specific types.
  - **Dead Definition Elimination**: Removes unused imports and local variable definitions.

#### Stage 3: CFG (Control Flow Graph)
- **Responsibility**: Represents program execution logic in the form of BasicBlocks, making control flow explicit.
- **Key Processing**:
  - **Control Flow Linearization**: Converts structured control flow (if/while/loop) into Goto and SwitchInt.
  - **Desugaring Complex Control Flow**: 
    - Expands decision trees generated by pattern matching into a series of basic blocks and conditional jumps.
    - Maps algebraic effect `yield`/`resume` to explicit state saving and recovery.
  - **Basic Block Construction**: Identifies leaders and partitions basic blocks.
- **Optimization**:
  - **Dead Code Elimination (DCE)**: Removes unreachable basic blocks.
  - **Jump Threading**: Simplifies consecutive conditional jumps, jumping directly to the final destination.
  - **Basic Block Merging**: Merges adjacent blocks with only one predecessor and one successor.

#### Stage 4: SSA (Static Single Assignment)
- **Responsibility**: Variable versioning, ensuring each variable is assigned only once, handling control flow convergence via Phi nodes.
- **Key Processing**:
  - **Dominance Analysis**: Computes the dominator tree and dominance frontier.
  - **Phi Node Insertion**: Inserts Phi functions at the dominance frontier to handle variable merging.
  - **Variable Renaming**: Versions variables with numbers to eliminate pseudo-dependencies.
- **Optimization**:
  - **Global Value Numbering (GVN)**: Identifies and eliminates computationally equivalent redundant expressions.
  - **Sparse Conditional Constant Propagation (SCCP)**: Constant propagation combined with control flow analysis, capable of folding dead paths caused by constant branches.
  - **Loop Invariant Code Motion (LICM)**: Moves loop-independent computations out of the loop body to reduce redundant calculations.
  - **Common Subexpression Elimination (CSE)**.

#### Stage 5: LIR (Low-level IR)
- **Responsibility**: A linear instruction set close to the target machine.
- **Key Processing**:
  - **SSA Destruction**: Eliminates Phi nodes via copying or register reallocation.
  - **Instruction Selection**: Chooses optimal instructions based on the target platform (e.g., WASM or custom bytecode).
  - **Register Allocation**: Linear scan or graph coloring algorithm.
- **Dual Role**:
  - **Compilation Target**: Serves as an intermediate representation for generating external targets like WebAssembly.
  - **VM Target**: `ValkyrieVM` acts as a reference interpreter, directly running the LIR instruction set to ensure consistent behavior across all platforms.
- **Optimization**:
  - **Peephole Optimization**: Replaces local instruction sequences.
  - **Stack Frame Optimization**: Reduces unnecessary pushes and pops.
  - **Instruction Scheduling**: Optimizes the execution pipeline to reduce latency.

### 2. Uncompromising Developer Experience

- **Diagnostics as Dialogue**: Uses the `miette` framework to provide an IDE-level diagnostic experience.
- **Uninterrupted Flow**: Achieves sub-second response times through an efficient compilation pipeline.
- **Intuitive and Powerful Language**: Provides high-level abstractions like algebraic effects and powerful pattern matching.

### 3. Unity and Duality of Abstractions

Based on the duality of data and control:
- `match` expression: Decomposition and pattern matching of data.
- `handle` expression: Decomposition and pattern matching of control flow (algebraic effects).

### 4. Duality of Execution Models

- **Dynamic Interpretive Execution**: Designed for development, debugging, and interactive environments, with a built-in full runtime.
- **Static Compiled Execution**: Designed for production deployment, compiled into lightweight, efficient WebAssembly modules.

### 5. Zero-Cost Abstraction

High-level abstractions should be as efficient as hand-written optimal low-level code after compilation.

## Core Module Details

### oak-valkyrie: Compiler Frontend Implementation
**Responsibility**: Provides Lexer, Parser, and AST definitions, parsing source text into an abstract syntax tree.

### valkyrie-types: Intermediate Representation Type Definitions
**Responsibility**: Centrally manages intermediate representation type definitions for each stage, including HIR, CFG, SSA, and LIR.

### valkyrie-vm: VM and Compiler Core
**Responsibility**: Implements transformations (passes) between stages and final execution.

### valkyrie-error: Unified Error Handling
**Responsibility**: Provides centralized error definitions and diagnostic information output.

## Maintenance Process

### Code Review Standards
1. **Architectural Consistency**: Ensure new code complies with the five design pillars.
2. **Error Handling**: Use the unified `valkyrie-error` system.
3. **Performance Considerations**: Avoid unnecessary allocations and copies.

### Debugging Guide
1. **Compiler Errors**: Check diagnostic output from `valkyrie-error`.
2. **Code Generation Issues**: Use the `--dump-{ast,hir,cfg,ssa,lir}` options to dump intermediate layer output.
